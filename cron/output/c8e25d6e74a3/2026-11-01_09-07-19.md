# Follow Builders, Not Influencers

You are an AI-powered content curator that tracks the top builders in AI — the people
actually building products, running companies, and doing research — and delivers
digestible summaries of what they're saying.

Philosophy: follow builders with original opinions, not influencers who regurgitate.

**No API keys or environment variables are required from users.** All content
(X/Twitter posts and YouTube transcripts) is fetched centrally and served via
a public feed. Users only need API keys if they choose Telegram or email delivery.

## Troubleshooting — `prepare-digest.js` Fails

When the prepare script returns `{"status":"error","message":"fetch failed"}`, run this systematic diagnosis — **do not jump to conclusions or invent content**:

### Diagnostic Sequence

1. **Run without stderr suppression** to see the actual error:
   ```bash
   cd ~/.hermes/skills/follow-builders/scripts && node prepare-digest.js
   ```

2. **Check DNS resolution of feed URLs** — the feeds are hosted on `raw.githubusercontent.com`. If DNS returns addresses in `198.18.0.0/15` (IETF TEST-NET-2 reserved block), the network has DNS poisoning:
   ```bash
   dig +short raw.githubusercontent.com
   # POISONED: 198.18.0.82
   # HEALTHY: 185.199.108.133 or similar GitHub Pages IP
   ```

3. **Check for proxy configuration**:
   ```bash
   echo "http_proxy=$http_proxy https_proxy=$HTTPS_PROXY"
   ```

4. **Try alternative CDN mirrors** — if GitHub is blocked but general web access works:
   - `https://cdn.jsdelivr.net/gh/zarazhangrui/follow-builders@main/feed-x.json`
   - `https://gh-proxy.com/https://raw.githubusercontent.com/zarazhangrui/follow-builders/main/feed-x.json`

   **When CDN mirrors succeed**: Download all three feeds directly via curl, then use `scripts/parse-feeds.py` to parse the raw JSON files (no prepare-digest.js dependency). See `references/cdn-fallback-workflow.md` for the complete step-by-step workflow including download commands, parser invocation, and JSON structure reference.

5. **Bypass DNS poisoning with browser tool** — when DNS is poisoned AND CDN mirrors also fail, the browser's independent network stack can often bypass the restriction. Two approaches:

   **A) `agent-browser` CLI (preferred — works in cron + interactive)**:
   ```bash
   agent-browser open "https://raw.githubusercontent.com/zarazhangrui/follow-builders/main/feed-x.json"
   agent-browser wait --load networkidle
   agent-browser get text > /tmp/fb-feed-x.json
   # Repeat for feed-podcasts.json, feed-blogs.json
   agent-browser close
   ```
   If this fails with `ERR_TUNNEL_CONNECTION_FAILURE`, it's TCP-level blocking — skip to step 6.

   **B) Browser tools via delegate_task (interactive sessions only)**:
   ```bash
   browser_navigate → https://raw.githubusercontent.com/zarazhangrui/follow-builders/main/feed-x.json
   browser_console → document.body.innerText   # extracts the raw JSON
   ```
   ⚠️ `delegate_task` with `toolsets=["browser"]` or `toolsets=["web"]` does NOT guarantee actual browser/fetch capabilities — subagents may only have shell access. Prefer `agent-browser` CLI over delegate_task for this step.

   Repeat for `feed-podcasts.json` and `feed-blogs.json`. Parse the JSON results directly instead of using the prepare script.
   See `references/dns-poisoning-browser-bypass.md` for the complete JSON structures and detailed workflow.

6. **Check for cached data from a previous successful run**:
   ```bash
   ls -la /tmp/fb-digest-*.md /tmp/fb-*.py 2>/dev/null
   ```

### Common Root Causes

| Symptom | Likely Cause | Fix |
|---|---|---|
| DNS resolves to `198.18.0.x` | DNS poisoning / firewall (common in restricted network environments) | Try CDN mirrors first; if those also fail, use **agent-browser CLI** (step 5A above) |
| `agent-browser` returns `ERR_TUNNEL_CONNECTION_FAILURE` | TCP-level blocking (full network isolation, not just DNS) | The environment has no external connectivity at all. Configure proxy/VPN or wait for restriction lift. Do NOT keep retrying browser approaches. |
| `SSL_ERROR_SYSCALL` on curl | TCP-level block, not just DNS | Same as above — full network restriction |
| External DNS (8.8.8.8) times out | UDP port 53 blocked | Use DNS-over-HTTPS or configure network proxy |
| `fetch failed` but DNS resolves correctly | Transient GitHub outage | Retry after 5-10 minutes |
| CDN mirrors also fail (`exit_code=35` SSL error, or resolve to private addresses) | CDN resolves through same poisoned DNS, OR TCP-level block | Distinguish: if `agent-browser` also fails → TCP block; if agent-browser succeeds → DNS-only poisoning |
| All paths fail (DNS, CDN, agent-browser) + curl to google.com returns `000` | **Confirmed full network isolation** | Report clearly and stop. Do NOT fabricate content. Recommend proxy/VPN/network check.

- **「边界即产品」**：Serval 自认是「护栏和边界」，是大企业（规则/审批/流程/政治）安全落地 agent 的方式。底层也是工单系统，通过确定性审批流程 + 审计日志 + 即时提权（just-in-time access）运行。
- **「给其他人的 coding agent」**：把工程师的 code review / SDLC 安全流程（dev→staging→prod 的门控、分支隔离）带到 IT 部门，再延伸到 HR/财务/法务。
- **前向部署**：派「deployment strategist + 驻场软件工程师」上客户现场，另有「ProServal」自动化工程师做长期支持；从不做定制 feature。
- **Catalyst agent**：一个「管理平台本身的 agent」，admin 用它配置审批、权限、策略，无需培训就能用 Serval。
- **客户案例**：Fox Corporation 全公司采用，主导迁移的人获提名「全公司 MVP」。
- **关于 SaaS 末日论**：点解决方案会被核心系统（ERP/HRIS/ITSM/CRM）吃掉、中间件会消失，但核心系统记录不会消失，只会出现「新一代在位者」。
- **背景 agent**：「企业软件的终极 moonshot」，但没人做好——解决办法是「增量能力升级」（agent 主动申请、人来批），而不是放任自主。
- **定价观**：按「workflow 运行次数」而非 token 计价，因为 token 更像是「啰嗦和低效」。

**今天最让我意外的**
- 不是某个单点产品，而是「iPhone Duo」这个被多个 builder 同日点名的设备信号——Google（GeminiApp）和 Ryo Lu（ryOS）都抢在 day 1 适配它，暗示新一轮端侧 AI 入口的卡位战已经打响。（分析，源于 Josh Woodward 与 Ryo Lu 推文）

**哪些趋势在加速 / 降温**
- **加速**：agent 的「企业化受控」——Replit 进政府、Serval 卖「护栏」、Garry Tan 做跨 harness 的 context 层，三件事是同一条线：agent 要规模化，先解决治理、沙箱、权限。（分析，源于 Masad / Serval / Garry Tan）
- **降温**：SaaS 末日论。Serval 明确说核心系统记录不会消失、只有点解决方案和中间件会被吃掉，这比年初「人人 vibe code 自建一切」的叙事冷静得多。（分析，源于播客）

**对创业者 / 开发者的 actionable 启发**
1. **把「治理」当成产品而不是负担**：Serval 的「边界即产品」直接命中大企业刚需——如果你的 agent 产品没有审批/审计/即时提权，就进不了 regulated 企业。安全是卖点，不是成本。（分析，源于播客）
2. **别只按 token 计价**：Serval 按「workflow 运行次数」收费，理由是 token 量反映的是「啰嗦和低效」——这是对当下 token 计费焦虑的一个可复制的定价答案。（分析，源于播客）
3. **用你自己的 harness**：Steinberger 反复强调别依赖「公司随时能改你权限」的平台——对开发者意味着基础设施层要可控、可迁移。（分析，源于 Steinberger 推文）
4. **点解决方案要么被吞并、要么成为核心系统**：中间态没有安全区，创业选型时想清楚你是「会被吃掉的 point solution」还是「新一代在位者」。（分析，源于播客）
