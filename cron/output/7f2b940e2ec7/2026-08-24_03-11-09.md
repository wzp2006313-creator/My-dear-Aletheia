## 📋 预安装代码审计协议

在安装任何新 Skill、MCP、依赖模块或第三方脚本之前，**必须先做静态审计**：

### 审计流程
1. **获取代码**：不要盲目执行 `curl | bash`。先使用 `curl`/`web_extract` 拉取 SKILL.md 和相关文件到本地
2. **完整静态扫描**：对文件内容进行正则/模式匹配检查
3. **重点监控二次下载行为**（供应链投毒的高发区）：
   - 包管理器：`npm install`、`pip install`、`brew install`、`cargo`、`gem`
   - 直接下载执行：`curl`、`wget`、`fetch()`、`urllib.request`
   - 绕过机制：`python -m http.server`、`ruby -e`、`git clone`
   - 混淆编码：`base64 -d | sh`、`eval()` 结合动态获取
4. **高风险文件格式警告**：
   - 编译二进制：ELF、.so、.dylib
   - 压缩包：`.tar.gz`、`.zip`、`.whl`
   - 可疑隐藏文件：以 `.` 开头的文件、包含大量不规则十六进制
5. **升级上报**：发现二次下载行为或高风险文件格式时，**必须强制中断安装**并向用户发出红色警报

**未通过安全审计的组件不得使用，无论其功能看起来多吸引人。**

## ⚠️ 已知局限（请务必了解）

1. **LLM 认知层脆弱性**：Agent 的 LLM 认知层容易被精心构造的复杂文档绕过。**人工常识和二次确认是供应链投毒的最后防线**
2. **同 UID 读取**：Hermes 以当前用户身份运行，恶意代码同样具备该用户权限。`chmod 600` 无法防止同用户读取
3. **哈希基线非实时**：仅在夜间审计时检查，最大发现延迟约 24h
4. **审计推送依赖外部 API**：消息平台偶尔故障会导致推送失败，报告始终本地保存
5. **依赖 LLM 指令优先级解析**：`--light-context`（Hermes 隔离会话）是最有效的缓解方案，但根本上仍依赖 LLM 的指令优先级判断
6. **版本兼容性**：本指南基于当前 Hermes Agent 版本编写，未来版本可能引入原生安全机制导致部分措施过时或冲突

## 🐛 夜间审计脚本已知缺陷与应对（工作笔记）

### 脚本超时风险

`nightly-security-audit.sh` 可能在以下环节卡住 5-15 分钟：

| 卡点 | 原因 | 规避方案 |
|------|------|---------|
| `find $HOME -size +100M -mtime -1` (指标9) | 遍历大容量 Home 目录 | 缩窄范围至 `~/.hermes/` + `~/Downloads/` + `~/Desktop/` |
| `log show --predicate 'process == "sudo"' --last 24h` (指标8) | macOS 统一日志查询慢 | 设置 30s 超时，超时则跳过该项 |
| `exec > "$REPORT_FILE" 2>&1` | 脚本将 stdout 全部重定向到文件 | 后台运行时 `output_preview` 始终为空；**必须通过读取报告文件来获取进度** |

### Cron 模式执行约束

- **`execute_code` 在 cron 模式下默认被阻止**（需 `approvals.cron_mode: approve` 配置）。Cron 审计任务中所有检查用直接 `terminal()` 调用完成
- 脚本超时时：kill 进程 → 读取已有的部分报告 → 对未完成的指标逐项用直接 terminal 命令补全
- **完整回退命令清单见** `references/audit-fallback-commands.md`

### 常见「基线失配」处置（工作笔记）

- **指标7 config.yaml 哈希失配**：多为 24h 内正常配置变更（改 provider/model/api_key 等）。处置：先用 `stat -f '%Sm' -t '%Y-%m-%d %H:%M:%S' ~/.hermes/config.yaml` 确认 mtime 与变更时间吻合，再 `grep -nE 'provider|api_key|token' config.yaml | sed 's/=.*/=***/'` 核对字段无异常注入，最后 `sha256sum ~/.hermes/.env ~/.hermes/config.yaml > ~/.hermes/.config-baseline.sha256` 更新基线。`.env` 失配才是高危信号。
- **指标12 skill 聚合哈希失配**：用户活跃装 skill 时属正常。核对 `ls ~/.hermes/skills | wc -l` 数量，确认新增/变更符合预期后更新 `~/.hermes/.skill-baseline.sha256`。
  - **高频误报根因（2026-08 确认）**：聚合哈希把 `~/.hermes/skills/.usage.json` 和 `.bundled_manifest` 计入，这两个是 Hermes 运行时元数据，每次 skill 被使用都会变 → 每晚必然失配。处置：先 `find ~/.hermes/skills -type f -newermt '<基线时间>' | grep -vE '\.(usage\.json|bundled_manifest)$'` 确认无实质内容文件变更；若仅有元数据变化则判为误报，无需改基线（改也无效，次日仍变）。根治方案是把脚本的 skill 哈希 `find ... -exec sha256sum` 加上 `-not -name '.usage.json' -not -name '.bundled_manifest'`。
- **指标9 state.db 增长**：`~/.hermes/state.db` 是 Hermes 核心 SQLite，会持续增长（观察值 200MB+，24h 内触发 `-size +100M` 大文件告警）。属正常但应监控，超过 500MB 建议评估 `hermes sessions` 归档/清理。
- **指标13 Git 备份**：若 `~/.hermes/.git` 长期 MISSING 且已有「每日 Hermes 备份」cron 兜底，可降级为 🟡 提示项而非阻塞。
