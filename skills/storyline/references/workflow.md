# Storyline Workflow

## 目标

从一个战略问题出发，经过研究、拆解、证据组织，产出一份结论清晰、结构锋利、可经受追问的 storyline，并通过独立压力测试完成定稿。

## 来源标注规则

每个数据点和引用须标注：**谁说的、什么时候说的**。在此基础上：

- **利益相关方的效果声明须标注立场。** 来源对所述内容有商业或政治利益时（如公司宣称自家产品的效果），必须标注"来源为利益相关方"。此类声明不得作为关键论断的唯一支撑，除非有独立来源交叉验证。
- **硬事实以一手源为准。** 产品规格、公开定价、财报数字、政策原文等可独立验证的客观事实，优先引用发布方原始材料。
- **无署名、无法追溯的来源不得支撑关键论断。**

## 工作流

### 0. 理解问题

拿到用户选题后，不要直接拆解。先做一轮 web research，目的是：

- 建立对该领域的基本认知：关键玩家、主要争论、近期变化。
- 识别用户问题背后的真实决策场景：谁需要这个答案、用来做什么决定。
- 发现用户可能未意识到的关键维度或前提假设。

研究完成后，向用户汇报你对问题的理解，包括：你认为这个问题的核心是什么、涉及哪些关键维度、有哪些你认为用户需要知道的背景。用户确认理解无误后，进入问题拆解。

### 1. 拆解问题与搜集证据

将主问题拆解为 3-7 个可独立研究的子问题。拆解时遵循：

- 子问题之间互不重叠，合起来覆盖主问题。
- 每个子问题应可被证据回答，而非只能靠观点。
- 拆解完成后须经用户确认。

确认后，围绕每个子问题搜集证据，直至满足以下条件：

- 每个子问题至少有一个可追溯的来源支撑（非匿名、非无署名）。
- 所有关键数据冲突已被显式处理：要么解释口径差异，要么以区间表达。
- 不存在关键维度空白。

### 2. 选择叙事结构

根据问题类型选择最适合的 storyline 结构：

- 金字塔：适合结论明确、时间紧迫的高管场景。结构为"答案 → 3 大支柱 → 证据"。
- SCQA：适合需要说服、受众可能抗拒的场景。结构为"背景 → 张力 → 核心问题 → 建议"。
- 正反合：适合争议性决策与平衡视角场景。结构为"正方论点 → 反方论点 → 综合判断"。

结构选择必须服务于决策场景，而不是追求形式完整。

### 3. 先搭骨架，再写内容

按以下顺序搭出 storyline 骨架：

1. 写出判断式标题，标题本身应体现结论或核心判断。
2. 写 5-7 句话的摘要，作为整份报告的微缩版。
3. 写背景部分，只说明发生了什么、为什么重要，控制在 200 字以内。
4. 按子问题展开正文，每章遵循"论点 → 证据 → 启示"。
5. 单列"风险与不确定性"，说明结论可能失效的条件。
6. 单列"建议"，给出可执行动作与前提条件。
7. 单列"附录：数据来源"，完整标注来源，利益相关方须标注立场。

### 4. 执行写作铁律

撰写每一段时，严格执行以下规则：

1. 结论先行：段首先给判断，再给证据。
2. 零废话：删掉所有不增加信息量的句子。
3. 有数据才有观点：没有数据支撑，不做定性判断。
4. 一论点一支撑：每个结论优先使用最强证据，不堆砌弱理由。
5. 做 so-what 测试：每段都必须回答"所以呢"。
6. 全部标注来源：每个数据点都标注来源和年份；利益相关方须标注立场。
7. 标注不确定性：证据不足时明确说明估算性质与可信度边界。

### 5. 形成初稿

初稿应满足以下形式要求：

- 全文围绕一个核心判断展开，不做并列信息堆叠。
- 每一章都回答一个明确子问题。
- 数据、案例、论据只服务于主线，不为"显得扎实"而堆材料。
- 正文保持紧凑，避免冗长铺陈。

初稿完成后，不将自我审查混入正文，直接进入独立压力测试。

### 6. 独立进行压力测试

压力测试必须以独立弱点报告形式输出，不得折叠进正文。

#### 6.1 逻辑审计

- 检查每条"论点 → 证据 → 结论"链条是否成立。
- 检查是否存在逻辑跳跃。
- 检查是否把相关性误写成因果关系。

#### 6.2 证据审计

- 标记只依赖单一来源的论断。
- 标记依赖无署名或利益相关方未验证自述的论断。
- 检查关键数据是否有第二来源交叉验证。
- 检查是否存在被含混带过的数据冲突。

#### 6.3 反面论证审计

- 为每条建议写出最强反对意见。
- 明确在什么条件下当前结论会失效。
- 以怀疑者视角检查最容易被挑战的位置。

#### 6.4 完整性审计

- 检查原问题树中的子问题是否都被充分回答。
- 检查是否遗漏显而易见的重要维度。
- 检查领域专家是否会指出关键缺口。

### 7. 输出弱点报告

弱点报告至少覆盖以下四项：

- 整体可信度：高 / 中 / 低。
- 逻辑问题：位置、问题、严重程度。
- 证据缺口：论断、当前来源、问题、修复方式。
- 未回应的反面论证与遗漏维度。

同时给出"定稿前建议修复项"清单。

### 8. 修复并复测

- 只修复被识别出的薄弱环节，不重写无关章节。
- 对受影响部分重新执行压力测试。
- 直到主要逻辑漏洞、证据缺口和遗漏维度被处理完毕，再输出最终版本。

## 红线

出现以下任一情况，应回退到相应阶段重做：

- 未做 web research 就拆解问题。
- 证据未搜全就开始写 storyline。
- 使用无署名、无法追溯的来源支撑关键判断。
- 数据薄弱却写成确定性结论。
- 只给建议，不回应反面论证。
- 引用数据不标注来源。
- 因为初稿"看起来不错"而跳过弱点报告。
